- acceso de propietario · segundo método de recuperación

## Procedimiento

1. **Crea:** un cliente OIDC confidencial en el proveedor de identidad con el URI de retorno exacto de DiscVault · `openid profile email` · `https://discvault.example.com/api/next/auth/oidc/callback`
2. **Configura:** `DISCVAULT_OIDC_ISSUER` · `DISCVAULT_OIDC_CLIENT_ID` · `DISCVAULT_OIDC_CLIENT_SECRET` · configura juntos el emisor, el ID de cliente y el secreto de cliente, o deja los tres vacíos; una configuración parcial impide el inicio
3. **Configura:** `DISCVAULT_OIDC_PROVIDER_NAME` · `OIDC`
4. **Elige:** `DISCVAULT_OIDC_INSECURE_BACKCHANNEL_ORIGINS` · `localhost` · Kubernetes DNS · `.internal` · permite orígenes HTTP privados exactos solo para los endpoints de token y JWKS; el emisor y la autorización del navegador siguen siendo solo HTTPS, la verificación TLS continúa activa y se rechazan las redirecciones de discovery, token y JWKS
5. **Inicia:** `next-api` · `--force-recreate`
6. **Prueba:** OIDC añade un método opcional de inicio de sesión en el navegador; las passkeys locales, las contraseñas opcionales, los códigos de recuperación, los tokens de API y los tokens bearer de MCP conservan sus funciones · una identidad es el par exacto de issuer y subject; el correo nunca se vincula automáticamente, la vinculación requiere la sesión iniciada del navegador y la desvinculación exige otro método de acceso utilizable
7. **Inspecciona:** `auth.oidc_failed` · los fallos registran solo el nombre visible configurado del proveedor, un código seguro `auth.oidc_failed` y el modo del flujo; nunca se registran secretos, tokens, códigos de autorización, state, nonce, URL de endpoints ni valores PKCE

```text
RP_ORIGINS=https://discvault.example.com

DISCVAULT_OIDC_CLIENT_SECRET=<client-secret>
DISCVAULT_OIDC_PROVIDER_NAME=Pocket ID
DISCVAULT_OIDC_INSECURE_BACKCHANNEL_ORIGINS=
```

```text
DISCVAULT_OIDC_INSECURE_BACKCHANNEL_ORIGINS=http://pocket-id.pocket-id.svc.cluster.local:1411
```

